생산·재고·품질의 상태와 수량 규칙 설계

서비스를 분리한 뒤에도 하나의 업무가 중복 실행되거나 취소 결과가 늦게 도착할 수 있습니다. 업무 상태, 요청 식별자, 수량 변경 이력을 함께 모델링해 허용할 변경과 거부할 변경을 구분했습니다.

재고 불출의 초안·발송·취소를 구분

사용자가 작성 중인 불출과 실제 출고를 구분하고, 생산 서비스의 수령·취소 결과가 확정되기 전에 재고가 잘못 복원되지 않도록 했습니다.

  • 초안은 재고를 차감하지 않고 수정·삭제할 수 있게 했습니다. 발송 시 현재고를 다시 확인하고 재고 차감·불출 상태·Outbox 이벤트를 같은 트랜잭션으로 저장했습니다.
  • 요청키와 요청 내용 검증, DB 잠금으로 같은 요청의 재시도와 동시 발송을 제어했습니다. 동일 키로 다른 내용을 보내는 요청은 거부했습니다.
  • 취소는 요청 상태만 기록하고 생산 측 성공 결과를 받은 뒤 원래 출고 이력에 대응하는 복원 이력을 남겼습니다. Inbox와 취소 요청키로 중복 결과 및 과거 시도의 늦은 결과를 구분했습니다.

중복 발송, 동시 취소 결과, 수령·취소 경합, 다른 회사 접근 및 Outbox 기록 실패 시 롤백을 검증하는 통합 테스트를 작성했습니다.

생산 산출·소비의 출처를 기록해 취소 범위 제어

생산 실적을 취소할 때 합산 재고만 되돌리면 이미 후속 공정에서 소비한 수량과 충돌할 수 있어, 산출과 소비의 연결을 남겼습니다.

  • 생산 산출을 실적·작업지시 공정 단위의 묶음으로 기록하고, 즉시 사용 가능한 방식과 목표 수량 충족 후 사용할 수 있는 방식을 구분했습니다.
  • 산출·소비·회수·환입 이력을 연결하고, 실적 취소 시 해당 실적이 소비한 묶음으로 환입하도록 구성했습니다. 불량 격리 등 취소 선행 조건도 검증했습니다.

확정된 품질 기준과 검사 이력을 보존

기준서가 변경되더라도 과거 검사가 어떤 기준으로 판정됐는지 확인할 수 있도록 기준 버전과 검사 회차를 분리했습니다.

  • 기준서의 초안·확정 리비전을 분리하고 확정 리비전의 수정·삭제를 제한했습니다. 검사 요청은 적용한 리비전을 참조하며, 재검사는 별도 회차와 사유로 기록했습니다.
  • 검사 요청·작업지시·실적·불량 상세를 모델링했습니다. 측정 허용 범위, 합격·불합격 수량 합계, 검사 항목 누락 및 확정 후 수정 제한을 검증했습니다.
  • 품질 등록 상태를 제품 서비스에 이벤트로 전달해 조회에 사용했습니다. 소비 측은 회사·식별자를 검증하고 원본 버전 비교와 Inbox로 중복·순서 역전에 대응했습니다.

이벤트의 중복·순서 역전·누락에 대한 복구 경로

서비스별 DB로 분리한 뒤 원본과 복제 데이터가 일시적으로 다를 수 있어, 정상 전파뿐 아니라 실패 후 재처리까지 함께 구성했습니다.

  • 업무 변경과 Outbox 기록을 같은 트랜잭션으로 저장하고 Debezium CDC·Kafka로 전달했습니다. 소비 측은 Inbox를 이용해 중복 처리를 제어했습니다.
  • 원본 버전을 비교해 오래된 이벤트가 최신 데이터를 덮어쓰지 않도록 했습니다. 누락 이벤트를 확인하고 재처리하는 경로를 마련해 운영 중 유실·중복·순서 역전을 단계적으로 개선했습니다.
  • 12개 서비스에 동기화 체계를 적용했습니다. 이벤트 기반 복제로 조회 의존성을 줄인 대신, 전파 지연과 재처리 상태를 운영에서 관리해야 하는 비용을 받아들였습니다.

QA 부하 테스트: 초당 2,000건 조건에서 동기화 지연 p95 0.44초.

측정 기준은 Outbox와 소비자 DB의 처리 시각 차이이며 실제 운영 트래픽 규모와 구분합니다.

PLM(Vault) 동기화의 응답과 작업 생명주기 분리

외부 제품·BOM 동기화가 완료될 때까지 HTTP 요청이 약 15분간 대기했습니다. 프록시 타임아웃이 나도 서버 작업은 계속돼 사용자가 성공 여부와 진행 상태를 파악하기 어려웠습니다.

  • 접수 단계에서 실행 이력을 만들고 HTTP 202와 실행 ID를 반환하도록 변경했습니다. 백그라운드 작업의 상태·진행률·처리 건수·실패 사유를 기록하고 조회 API를 제공했습니다.
  • 외부 HTTP 호출을 DB 트랜잭션 밖으로 옮기고 페이지 단위로 저장했습니다. DB Lease 락과 소유권 갱신으로 다중 인스턴스의 중복 실행을 제어했습니다.
  • 중복 탐지를 해시 기반으로 바꾸고 시퀀스 풀링·JDBC 배치를 적용했습니다. 아이템·BOM·순환 참조 검증과 반려 사유 기록을 분리했습니다.

비동기 접수 응답 17ms · DB 반영 30,643행 / 3.7초 · 검증 실패 데이터 873건 사유별 기록.

각각 접수 응답, DB 반영, 검증 기록에 대한 결과이며 전체 동기화 완료 시간이 17ms로 줄었다는 의미는 아닙니다.

계측 결과를 근거로 외부 API 연동 방식 변경

단계별 계측에서 전체 소요의 99.6%가 외부 API 조회 구간임을 확인했습니다. DB 최적화만으로 전체 대기 시간을 크게 줄이기 어려워 외부 조회 방식 개선으로 범위를 옮겼습니다.

  • 기존 MES → 자체 C# HTTP API → Vault SDK(SOAP) 중계 구조의 조회 지연을 개선하기 위해 Autodesk 공식 Vault REST API를 사용하는 별도 인터페이스 서버를 구축했습니다.

  • 회사 귀속 데이터·조회에 company_id를 적용하고 사번 유일성 제약을 회사·사번 조합으로 변경했습니다. 서브도메인 고객사 식별은 기능 플래그로 단계 적용했습니다.
  • API 경로 대신 @RequiresPermission으로 기능 권한을 선언하고 고객사가 역할별 권한을 조합하도록 했습니다. 권한 변경 커밋 후 Redis 캐시를 무효화하고 TTL 10분을 적용했습니다.
  • 캐시 미스·조회 실패 시 직원관리 서버의 원본을 조회하고, 원본 조회까지 실패하면 보호 API를 거부했습니다. 무효화 실패 시 TTL 동안 변경 반영이 지연될 수 있는 한계도 고려했습니다.

게이트웨이에서 반복 인증 호출 축소

요청 처리 전에 로그인·직원관리 서버로 인증·인가를 위임하면서 내부 호출과 장애 의존성이 늘어났습니다.

  • Spring Cloud Gateway·Consul로 서비스 탐색·라우팅을 구성하고 JWT 서명·만료·발급자를 로컬 검증했습니다. Redis 토큰 폐기 조회와 권한 캐시·원본 조회를 결합했습니다.
  • 인증한 회사·직원 정보를 대상 서비스에 전달하고 서비스별 서킷 브레이커를 적용했습니다. 반복 호출을 줄이는 대신 게이트웨이에 정책 적용과 캐시 일관성 관리 책임을 두었습니다.

선택해서 적용하는 공통 라이브러리

서비스마다 예외·통신·동기화 구현이 달라 공통 정책을 바꿀 때 개별 저장소를 수정해야 했습니다.

  • 관심사별 모듈과 Spring Boot 자동 설정을 제공해 13개 서비스의 처리 규격을 표준화했습니다. 웹·JPA 의존성은 compileOnly로 전이를 제한하고 모듈별 버전을 GitHub Packages에 발행했습니다.
  • 고객사별 추가 필드는 회사·업무 대상별 정의와 JSONB 값으로 관리하도록 공통화했습니다. 필수값·타입·기본값을 검증하고, 컬럼 추가 부담 대신 동적 검증·검색 로직을 관리하도록 구성했습니다.

요청 추적·테스트·배포 절차 표준화

분리된 서비스의 장애 원인을 찾고 변경을 검증할 수 있도록 추적·테스트·배포 기반을 함께 정리했습니다.

  • HTTP와 Outbox·CDC·Kafka 구간의 추적 연결을 보완해 12개 서비스의 요청을 추적 ID로 확인하도록 했습니다. Prometheus·Grafana로 메트릭과 임계치 알림을 연결했습니다.
  • 팀과 함께 12개 서비스에 단위·Testcontainers 기반 통합 테스트 약 900개를 구축하고 Awaitility로 비동기 처리를 검증했습니다.
  • GitHub Actions 공용 워크플로우와 Blue-Green 배포를 적용했습니다. 헬스체크 후 전환, 실패 시 기존 인스턴스 유지, graceful shutdown을 구성했으며 배포 1회는 약 4~5분입니다.

검증 범위: 약 900개는 팀 공동 구축 성과입니다. 러너 네트워크 제약으로 배포 단계에서는 테스트를 제외했으며, 머지 전 CI 연계는 남은 과제입니다.

본인 담당: 생산·재고·품질 DB 모델링, 업무 API, 공정 수량 계산 및 보상 처리 구현·운영

누적 프로젝트 1,300건·제품 데이터 9만 건을 관리하는 ERP/MES를 개발·운영했습니다. 사용자가 도면과 엑셀로 확인하던 부품·공정 수량 규칙을 시스템에 반영했습니다.

  • BOM(자재 명세서)과 공정 순서를 작업지시·자재 소요량으로 연결했습니다. 조립 순서와 부품 관계를 그래프로 모델링하고 BFS 탐색·BOM 비율 역산으로 재작업·취소에 따른 변경 범위와 수량을 계산했습니다.
  • 불량 공정·수량·재작업 시작 공정을 선택하면 관련 부품·공정 수량과 재고를 자동 반영해 개별 수기 계산을 제거했습니다.
  • 생산·품질·재고의 HTTP 연동 실패 시 업무 키 기반의 멱등한 보상 API로 앞선 변경을 복원했습니다. 보상 실패는 자동 재시도하고 실패 기록·알림 및 기록 기반 수동 복구로 대응했습니다.

운영 환경의 생산·품질·재고 전체 반영 지연 p95 120ms. 정상 연동의 반영 지연이며 보상 실패의 복구 시간은 아닙니다.

  • 같은 경매의 현재가 갱신·최고가 판정이 충돌하지 않도록 경매 ID별 Redisson 분산 락을 적용했습니다. 같은 경매는 직렬화하고 서로 다른 경매는 병렬로 처리했습니다.
