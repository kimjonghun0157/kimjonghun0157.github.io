왜 MSA로 전환했는가

1세대 ERP/MES를 약 2년간 직접 운영하며, 반복되는 문제가 기능이 아니라 구조에서 온다는 것을 확인했습니다. 그래서 목표를 "기능 추가"가 아니라 "변경이 번지지 않는 구조"로 잡았습니다.

시작은 모듈형 모놀리식이었습니다. 인프라 구성 부담과 초기 개발 속도를 고려하면 합리적인 출발이었지만, 도메인이 늘어날수록 아래 문제들이 기능을 아무리 잘 만들어도 사라지지 않고 구조적으로 반복됐습니다.

특히 도메인이 늘며 진입점을 게이트웨이로 묶고 모듈끼리 HTTP로 통신하기 시작했는데, DB는 여전히 하나였습니다. 단일 DB인데도 모듈 사이는 네트워크로 오가는 구조라 로컬 트랜잭션의 이점을 살리지 못했고, 연동마다 실패를 되돌리는 보상 트랜잭션을 손으로 짜야 하는 구조적 모순이 쌓였습니다. 배포만 쪼개졌을 뿐, MSA의 비용은 치르면서 이점은 얻지 못하는 — 말하자면 ‘분산 모놀리스’의 초입이었습니다.

01 · 변경이 경계를 넘는다
도메인은 셋이지만 데이터 모델은 하나였습니다.

영업에서는 수주, 생산에서는 작업 단위, 재고에서는 집계 기준으로 같은 데이터를 서로 다르게 해석했습니다. 그러나 영업·생산·재고 중 어느 도메인도 해당 테이블을 온전히 소유하지 않았습니다.

그 결과 한 도메인의 요구로 스키마나 공통 모델을 변경하면 다른 도메인의 로직과 API까지 함께 영향을 받았습니다. 서비스는 분리되어 있었지만 변경은 특정 서비스 안에서 끝나지 않았습니다.

02 · 독립적으로 확장할 수 없다
부하는 생산·설비 영역에 집중됐지만 그 영역만 독립적으로 확장하기 어려웠습니다.

애플리케이션은 서비스별로 배포됐지만 데이터 계층은 하나의 DB를 공유했습니다. 생산·설비 트래픽이 증가하면 부하가 적은 기준정보·코드 영역까지 동일한 DB 커넥션·CPU·메모리·I/O 자원을 두고 경쟁해야 했습니다.

결국 서비스 인스턴스를 늘리더라도 공유 DB가 병목이 되어, 도메인별 부하 특성에 맞는 확장이 제한됐습니다.

03 · 저장소를 선택할 수 없다
도메인마다 데이터 특성이 달랐지만 저장소는 단일 RDB로 고정돼 있었습니다.

설비 데이터는 시계열 조회와 대량 적재가 중요하고, 제품 구조·공정 데이터는 복잡한 계층 구조와 다양한 조회 형태를 가집니다. 그러나 여러 서비스가 같은 테이블·스키마에 의존하고 있어 특정 도메인만 별도 저장소로 분리하기 어려웠습니다.

그 결과 도메인 특성에 맞는 저장소를 선택하거나, 조회·저장 방식에 맞게 개별적으로 최적화할 수 없었습니다.

04 · 배포가 독립적이지 않다
작은 수정도 전체 시스템의 영향 범위를 검토해야 했습니다.

공통 모델이나 DB 스키마를 변경하면 관련된 여러 서비스를 함께 수정하고 검증해야 했습니다. 변경 규모와 관계없이 통합 테스트 범위가 넓어졌고, 서비스 간 배포 순서와 하위 호환성까지 고려해야 했습니다.

서비스별로 배포 파일은 나뉘어 있었지만 실질적으로는 독립 배포가 어려웠고, 변경이 누적될수록 배포 자체가 리스크가 됐습니다.

정리

시스템은 서비스 단위로 분리되어 있었지만, 공유 데이터 모델과 단일 DB에 강하게 결합되어 있었습니다. 물리적으로는 분산됐지만 변경·확장·저장소 선택·배포를 독립적으로 수행할 수 없는 — 전형적인 분산 모놀리스 구조였습니다.

그런데 왜 더 가벼운 대안이 아니었나

MSA는 운영 복잡도라는 대가가 크기 때문에, 먼저 더 싼 선택지들을 검토하고 탈락시켰습니다. 각 대안이 앞의 네 문제를 푸는지로 판단했습니다.

문제

생산·구매·프로젝트 등 서로 다른 영역의 121개 테이블이 단일 MySQL을 공유해, 한 도메인의 스키마 변경이 무관한 서비스까지 번졌습니다. 특정 도메인에 조회·트래픽이 몰리면 커넥션 풀·CPU를 독점해 전체가 함께 느려지는 단일 장애점이었습니다.

접근

현업·기획 부서와 업무 규칙을 반복 조율해 각 서비스가 소유할 데이터 경계를 확정하고 서비스별 독립 DB로 분리했습니다. 통신은 데이터 성격에 따라 이원화 — 실시간성이 필요한 데이터는 동기 API 조합으로, 부하 격리가 중요한 재고 등은 비동기 이벤트 복제로 설계했습니다.

결과

스키마 변경 영향이 서비스 내부로 격리돼 독립 배포가 가능해졌고, 한 도메인의 부하가 타 영역의 커넥션 고갈로 번지는 경로를 끊었습니다.

STORAGE CHOICE · 왜 PostgreSQL이었나

독립 DB로 나누며 저장소도 다시 골랐습니다. 기존 시스템이 MySQL이라 처음엔 그대로 시작했지만, 제조 도메인은 품목·공정마다 관리 속성이 제각각이라 정형 컬럼만으로는 담기 어려운 가변 속성이 계속 늘었습니다. 이를 JSON으로 저장하되 조회 조건으로도 써야 했고, JSON 내부 필드를 인덱싱·쿼리하는 데 유리한 PostgreSQL(JSONB)로 자연스럽게 옮겼습니다.

생산 도중 수량을 더하거나 불량으로 재작업할 때 BOM 수량을 그대로 고쳐, 이미 만든 분량과 새로 추가된 분량이 한 공정에 섞여 무엇이 처음 생산분이고 무엇이 추가분인지 구분할 수 없었습니다. "생산이 몇 번 일어났는가"라는 개념 자체가 모델에 없어서 생긴 문제로 봤습니다.

접근

세 가지 안을 검토·기각했습니다. 구분 표시만 붙이는 안은 결국 수량을 합쳐 보게 됐고, BOM을 통째로 복제하는 안은 원본이 여러 벌이 됐으며, 별도 객체로 감싸는 안은 너무 무거웠습니다. 결국 "제품 구조는 거의 안 바뀌지만 생산은 매번 새로 일어난다"는 차이를 근거로, 제품 구조와 생산 실행을 별개로 두는 최소 모델로 정했습니다.

결과

초기 생산분과 추가·재작업 물량이 BOM 수량에 섞이던 데이터 부정합을 없애고, 물량을 생산 건별로 구분 추적하게 됐습니다. 수량이 하위 부품까지 비율대로 전파되는지, 같은 요청을 반복해도 공정이 중복 생성되지 않는지를 회귀 테스트로 검증했고, 15개 공정 전체 흐름을 TestContainers 시나리오로 검증했습니다(이 서비스 통합 테스트 118개).

이벤트 기반 데이터 동기화 구축

문제

한 DB로 묶여 있던 공유 도메인을 서비스로 분리하면서, 각 서비스가 로컬 DB로 조회하려면 원본 변경을 전파받아야 했습니다. 서비스가 나뉘어 하나의 트랜잭션으로 묶을 수 없는데, 그렇다고 동기화 과정에서 이벤트가 유실되면 서비스 간 상태가 영구히 어긋납니다. "어떻게 전파하느냐"가 곧 정합성을 좌우하는 문제였습니다.

접근

전파 방식을 후보별로 비교해, 장애 전파와 이벤트 유실을 모두 피하는 Transactional Outbox + Debezium CDC를 택했습니다.

전파 방식 검토 · 4개 후보
✗ 동기 API 호출 상대 서비스 장애가 내 트랜잭션으로 전파되고 결합도가 높아짐
✗ 앱에서 Kafka 직접 발행 Dual Write — DB 커밋과 발행이 원자적이지 않아 유실·유령 이벤트
△ Outbox + 앱 폴링 유실은 막지만 폴링 쿼리·중복 발행·인스턴스 간 락을 직접 구현해야 함
✓ Outbox + Debezium CDC 앱은 DB 트랜잭션까지만 책임 — 발행은 CDC에 위임, 유실 경로 제거

증상

원인

Incident 02 어긋난 데이터 재동기화
증상

네트워크 순단이나 소비 측 버그로 특정 이벤트가 누락되면, 그 이후 상태가 원본과 영구히 어긋난 채 남았습니다.

원인

이벤트 기반 동기화에서 유실 확률은 0이 아니므로 '언젠가 어긋난다'를 전제로 봐야 했는데, 초기 설계엔 복구 수단이 없어 장애 때마다 임시 스크립트로 메꾸는 반복·위험이 있었습니다.

대응

실제로 어긋남이 발생하면 임시 스크립트가 아니라 정의된 재동기화(upsert)·self-heal 경로로 즉시 복구했습니다. 순서 역전·멱등·유실·LWW 등 다른 인시던트의 즉시 복구도 모두 이 경로를 씁니다.

해결

복구를 처음부터 설계에 포함했습니다. Outbox·Inbox의 eventId를 주기적으로 대조해 소비되지 않은 이벤트를 탐지·자동 재발행하는 폐루프(self-heal)를 두고, 발행 서비스의 현재 상태 전체를 실어 소비 측이 덮어쓰는 재동기화(upsert) 이벤트 타입을 미리 정의하고 호출 API까지 열어뒀습니다.

Incident 04 커밋 타이밍이 만든 이벤트 유실
증상

소비 도중 예외가 나거나 인스턴스가 재시작되면 일부 메시지가 처리되지 않은 채 사라지는 유실이 발생했습니다.

원인

기본 자동 커밋이 처리 완료와 무관하게 오프셋을 진행시켜, 처리 전에 커밋된 메시지는 실패해도 다시 오지 않았습니다(at-most-once).

대응

유실로 누락된 이벤트는 Outbox·Inbox의 eventId를 대조하는 self-heal이 탐지해 자동 재발행·복구했고, 이어서 커밋 방식을 바꿨습니다.

해결

커밋 시점을 처리 결과에 묶었습니다. 업무 처리와 Inbox 기록이 성공한 뒤에만 수동으로 오프셋을 커밋(MANUAL ack)하고, 실패하면 커밋하지 않고 지수 백오프로 재시도합니다. 성공 기준은 Inbox 멱등으로 잡아 재시도가 중복 처리를 만들지 않게 했고, 이 규약을 컨슈머 공통 계약으로 표준화했습니다.

Incident 04 · 완전 로컬화 캐시로도 못 지운 원격 호출이 남아있었습니다
문제

캐시 히트율이 높아도 미스가 나는 순간엔 여전히 인증 서버 왕복이 발생했고, 이를 지키려 서킷 브레이커·타임리미터 같은 방어 로직을 계속 유지해야 했습니다. 인가(authorization)는 캐시와 별개로 로그인 서버가 매 요청마다 EMS를 다시 호출하는 구조였고, 캐시는 게이트웨이 로컬 상태라 인스턴스를 늘리면 이 개선 자체가 무의미해지는 구조였습니다.

접근

인증 판정 자체를 게이트웨이로 가져왔습니다. 로그인 서버와 공유하는 서명키로 JWT를 게이트웨이가 직접 검증하고, 로그아웃은 공유 Redis denylist(토큰 jti 단위)로 즉시 반영했습니다. 인가도 같은 방향으로 — 로그인 시점에 역할·관리자 여부를 토큰에 미리 심고, 게이트웨이가 EMS의 권한 카탈로그를 주기적으로 pull해 로컬 캐싱한 뒤 매 요청은 토큰 클레임만으로 판정합니다.

결과

인증·인가 모두 요청당 원격 호출이 0회가 되어 인증 서버·EMS 장애가 더 이상 게이트웨이 요청 경로에 번지지 않습니다. 방어 로직 자체가 필요 없어져 코드를 걷어냈고(게이트웨이 인증 필터 -433/+329줄, EMS 구인가 로직 605줄 삭제), 캐시 로컬리티에 기대지 않으니 게이트웨이를 다중 인스턴스로 늘려도 인증 성능이 그대로 유지됩니다.

관측 수단이 로그(ELK)뿐이라 장애가 나면 서비스별 로그를 수동으로 대조해야 했고, 메트릭은 게이트웨이 한 곳만 노출돼 모으는 곳 없이 버려졌습니다. 특히 Kafka로 이어지는 비동기 구간은 요청 흐름이 끊겨 하나의 요청을 끝까지 추적하기 어려웠습니다.

접근

추적 ID와 메트릭 노출을 공용 라이브러리로 표준화해 각 서비스가 의존성만 추가하면 적용되게 했고, 동기 호출뿐 아니라 비동기 구간(HTTP→Outbox→CDC→소비)에도 동일한 traceId가 전파되도록 심었습니다. 메트릭은 Prometheus·Grafana로 수집·시각화하고 이상 징후는 Slack으로 알렸습니다.

결과

관측 범위가 게이트웨이 한 곳에서 전 서비스로 확장됐고, 동기·비동기를 관통하는 하나의 traceId로 장애 지점을 로그·메트릭에서 함께 짚을 수 있게 됐습니다.

통합 인가(RBAC) 체계 구축

문제

API가 여러 서비스에 흩어진 MSA에서 접근 권한을 서비스마다 제각각 다루면 정책이 어긋나고 누락되기 쉬웠습니다. 권한을 한 곳에서 통제할 체계가 필요했습니다.

접근

역할–API 매핑을 중앙에서 관리하는 RBAC를 세웠습니다. 각 서비스가 @ApiPermission+리플렉션으로 기동 시 통제 대상 API를 스스로 등록(opt-in)하면 EMS가 단일 카탈로그로 취합합니다. 카탈로그는 정형 RDB 대신 MongoDB로 담아 한 역할에 여러 서비스의 권한을 구조화하고 멀티 롤을 부여합니다.

결과

접근 정책을 중앙에서 일관 관리하고, API 추가·변경 시 권한이 자동 반영되어 수동 관리 비용을 없앴습니다.

Incident 01 권한 대상 수집 — 전체 노출 대신 opt-in
문제

권한 통제 대상 API를 모으기 위해 처음엔 Actuator로 전체 엔드포인트를 노출해 긁는 방식을 검토했지만, 통제와 무관한 API까지 외부에 드러나 보안 리스크가 있었습니다. 반대로 수동 매핑은 누락과 유지비가 컸습니다.

접근

통제가 필요한 API에만 @ApiPermission을 선언하는 opt-in 스캔으로 정했습니다. 기동 시 그 어노테이션이 붙은 API만 리플렉션으로 수집합니다.

결과

API 구조를 외부에 노출하지 않으면서, 인가가 필요한 대상만 정확히 카탈로그에 편입됩니다.

Incident 02 서비스마다 반복되던 EMS 등록 코드
문제

공통 라이브러리 이전엔 각 서비스가 @ApiPermission이 붙은 API를 스캔해 EMS(권한 카탈로그)로 전송·등록하는 코드를 직접 작성해야 했습니다. 같은 로직이 서비스마다 복제돼, 새 서비스를 추가할 때마다 이 등록 코드를 또 짜야 하는 반복이 있었습니다.

접근

이 스캔·전송 로직을 공통 라이브러리의 permission(API 권한 스캐너) 모듈로 추출했습니다. 서비스는 의존성만 추가하면 기동 시 자동으로 @ApiPermission을 스캔해 EMS로 등록합니다.

결과

서비스마다 반복하던 등록 코드가 사라지고, 새 서비스는 어노테이션 선언과 의존성 추가만으로 인가 카탈로그에 자동 편입됩니다. 공통 라이브러리 전반은 아래 ‘멀티 모듈 라이브러리’에서 다룹니다.

서비스별 자동화 테스트 (유닛 + 통합)

문제

서비스가 분리되며 각 서비스가 실제 DB(MySQL·PostgreSQL·MongoDB)·Redis·Kafka 같은 실인프라에 의존하는 비중이 커졌습니다. Mock 기반 단위 테스트만으로는 트랜잭션 격리, Kafka 발행·소비 타이밍, 중복 소비 예외처럼 런타임에서만 드러나는 회귀를 잡지 못했습니다.

접근

TestContainers로 실제 MySQL·PostgreSQL·MongoDB·Redis·Kafka를 CI(GitHub Actions)·로컬 빌드에서 Docker로 띄운 통합 테스트를 자동화했습니다. 매번 컨테이너가 기동돼 느려지는 걸 막기 위해 공통 추상 베이스 + @ServiceConnection 컨테이너 빈 + 스프링 컨텍스트 캐싱으로 컨테이너를 한 번만 기동·재사용했고, 비동기 구간은 Thread.sleep 대신 Awaitility로 Inbox 적재 시점까지 폴링해 Flaky를 없앴습니다.

결과

약 900개 유닛·실인프라 통합 테스트로 소스·공통 라이브러리 변경을 빌드 단계에서 검증했고, 생산 15개 공정 E2E와 이벤트 정합성(유실·순서 역전 시 자가 복구)까지 실인프라 레벨에서 통제했습니다.

무중단 배포 파이프라인

문제

사내 Gitea + 수동 SSH 배포라 표준 절차가 없어 배포마다 수동 공수가 컸고, 새 버전을 올릴 때마다 다운타임이 생겼습니다. 실패 시 안전하게 이전 버전으로 되돌릴 장치도 없었습니다.

접근

저장소를 GitHub로 이전하고 공용 워크플로우(Reusable Workflows)로 배포를 표준화해, 각 서비스는 이름·승인 여부만 지정하면 빌드부터 배포까지 자동 수행되게 했습니다. Blue-Green 무중단 전환(새 인스턴스 기동→헬스체크→nginx·Consul 트래픽 전환→기존 graceful stop)에 헬스체크 실패 시 자동 롤백을 붙였습니다.

결과

수작업 배포가 GitHub 승인 한 번으로 무중단 자동 배포가 됐고, 잦은 배포에도 서비스 중단·요청 유실 없이 Downtime 0초를 유지했습니다.
