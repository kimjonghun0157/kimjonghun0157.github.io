02 / Architecture Decision

서버를 나누는 것에서,
업무 책임을 나누는 것으로

공유 DB를 유지하는 방안도 검토했습니다. 그러나 여러 서비스에 쓰기 요구가 분산돼 있어, 업무별 데이터 소유권과 변경 책임을 먼저 정리해야 한다고 판단했습니다.

Before / 분산 모놀리스

부서·업무별 서버 + 공유 DB

  • ERP·MES 모놀리스에서 독립 배포·확장을 위해 서버 분리
  • 서비스 간 HTTP 호출과 일부 다른 업무 영역 테이블의 직접 읽기·쓰기 혼재
  • 변경마다 관련 서비스 영향 확인과 공동 검증 필요

기존에도 게이트웨이는 존재했습니다. 당시 내부 구현은 본인 담당 범위가 아니므로 세부 구조를 기재하지 않았습니다.

After / 단계적 전환

업무별 모델 + 서비스 소유 DB

  • 각 업무가 관리할 데이터와 상태 변경 책임 정의
  • 필요한 정보는 API·이벤트로 연동
  • 조회용 정보와 해당 서비스가 직접 관리하는 업무 상태 구분

DB 분리는 업무 책임의 경계를 구현하는 수단이며, 동기화 지연과 복구 관리 비용이 함께 생겼습니다.

업무의 의미와 상태를 기준으로 경계를 나눴습니다

수주의 프로젝트는 주문·납품을, 생산의 프로젝트는 생산 작업을 관리하는 단위로 정의했습니다. 생산에 필요한 프로젝트·확정 품목 정보는 연동하되, 업무 데이터와 진행 상태는 각 서비스가 관리하도록 설계했습니다.

예를 들어 수주가 취소되면 취소 사실과 사유를 이벤트로 전달합니다. 생산·재고 서비스는 연동된 수주의 취소 상태를 반영하고, 관리자가 현장 진행 상황에 따라 후속 처리를 결정하도록 했습니다.

업무·소비 서비스와 DB는 역할을 묶어 표시했습니다. DB 노드 하나가 공유 DB를 뜻하지 않습니다. 세부 요청·동기화 흐름은 아래 사례에서 설명합니다.

03 / Selected Decisions

설계 판단을 보여주는
세 가지 사례

업무 정합성, 이벤트 복구, 외부 연동 병목을 어떤 기준으로 해결하고 검증했는지 설명합니다.

01INVENTORY × PRODUCTION

생산의 취소 결과를 확인한 뒤 재고를 복원했습니다

재고에서 출고한 자재를 생산이 이미 수령했다면, 취소 요청과 동시에 재고를 복원할 수 없습니다. 요청과 결과 확정을 분리했습니다.

작성불출 초안
재고 변경 없음
발송재고 차감
Outbox 함께 저장
취소 요청결과 대기
재고 복원 보류
취소 성공 시복원 이력 기록
한 번만 반영
  • 요청키와 DB 잠금으로 재시도·동시 발송을 제어하고, 같은 키에 다른 내용이 오면 거부했습니다.
  • 취소 거절은 재고를 복원하지 않습니다. 과거 취소 시도의 늦은 결과는 현재 요청키와 비교해 구분했습니다.
  • 중복 결과, 수령·취소 경합, 회사 경계, Outbox 실패 시 롤백에 대한 통합 테스트를 작성했습니다.

결과 · 취소 성공이 확인된 경우에만 재고를 복원하도록 구현했습니다.
검증 · 중복 결과·수령/취소 경합·Outbox 실패 롤백 통합 테스트 작성.
적용 · 일부 운영 적용.

02EVENT CONSISTENCY

이벤트 전달 이후의 중복·역전·누락을 처리했습니다

서비스별 독립 DB를 운영하려면 이벤트 전달뿐 아니라 소비자의 반영 기준과 복구 경로가 필요했습니다. Outbox·Debezium CDC·Kafka 동기화와 Inbox·원본 버전 기반 처리 정책을 구축했습니다.

저장과 발행의 간극 축소

업무 데이터와 Outbox를 같은 트랜잭션에 저장하고, 커밋된 변경을 CDC로 전달했습니다. DB 저장 후 별도로 메시지를 발행하던 실패 구간을 줄였습니다.

중복·순서 역전 처리

Inbox로 중복 처리를 제어하고 원본 버전을 비교했습니다. 같은 이벤트의 재수신과 과거 이벤트가 늦게 도착하는 경우를 구분해 처리했습니다.

누락 확인과 재처리

운영 중 발생한 누락을 확인하고 이벤트를 재처리하는 경로를 마련했습니다. 전달 체계 도입 이후에도 유실·중복·순서 역전 문제를 단계적으로 개선했습니다.

설계의 비용 — 로컬 조회로 서비스 간 조회 의존성을 줄인 대신 데이터 전파 지연과 복구 상태를 관리해야 했습니다. 수주 취소 사실을 동기화하더라도 생산·재고의 후속 처리는 각 업무의 규칙과 관리자 판단에 맡겼습니다.
12개 서비스이벤트 동기화 체계 적용
p95 0.44초QA 부하 조건의 동기화 지연

검증 · 초당 2,000건의 QA 조건에서 측정한 Outbox·소비자 DB 처리 시각 차이입니다. 실제 운영 트래픽 수치와 구분합니다. 적용 · 12개 서비스 동기화 체계에 적용하고 운영 장애를 단계적으로 개선했습니다.

03EXTERNAL INTEGRATION

느린 구간을 측정하고, 개선 대상을 바꿨습니다

Vault 동기화 완료까지 약 15분간 HTTP 요청이 대기했습니다. 먼저 접수와 작업을 분리하고, 실행 이력·진행률·DB Lease 락으로 작업 상태와 중복 실행을 관리했습니다.

  • 외부 호출을 DB 트랜잭션 밖으로 옮기고 페이지 단위 저장, 해시 기반 중복 탐지, 시퀀스 풀링·JDBC 배치를 적용했습니다.
  • 계측 결과 전체 소요의 99.6%가 외부 API 조회임을 확인했습니다.
  • 이후 C# HTTP API·Vault SDK(SOAP) 중계에서 공식 Vault REST API를 사용하는 별도 인터페이스 서버 구축으로 개선 범위를 확장했습니다.
17ms비동기 접수 응답
3.7초30,643행 DB 반영 구간

검증 · 접수 응답과 DB 반영 구간을 각각 측정했습니다. 전체 시간의 99.6%가 외부 조회임을 확인해 개선 대상을 외부 연동으로 전환했습니다. REST API 전환 후 전체 완료 시간은 이 측정치에 포함되지 않습니다.

04 / Shared Platform

요청의 진입점부터,
고객사 데이터의 경계까지

인증·기능 권한은 게이트웨이에서 판정하고, 조회할 회사의 범위는 업무 서비스에서도 제한했습니다.

반복적인 인증·인가 호출을 로컬 검증과 캐시로 전환했습니다

요청마다 로그인·직원관리 서버에 위임하던 판정을 JWT 서명·만료·발급자 검증과 권한 캐시로 전환했습니다. Redis 토큰 폐기 조회는 유지하고, Spring Cloud Gateway·Consul로 라우팅과 서비스별 서킷 브레이커를 구성했습니다.

권한 변경과 조회 실패

변경 커밋 후 캐시를 무효화하고 TTL 10분을 적용했습니다. 캐시 미스·오류 시 직원관리 원본을 조회하며, 원본 조회까지 실패하면 보호 API 접근을 거부합니다.

선택의 비용

내부 호출을 줄인 대신 게이트웨이가 정책과 캐시 일관성을 관리합니다. 무효화 실패 시 권한 반영이 지연될 수 있고, Redis·원본 조회 의존성도 남습니다.

고객사별 데이터 접근

같은 조회 권한이 있어도, 다른 회사의 데이터는 조회하지 못하도록

Account · 회사·구독 원본

회사 코드·상태·구독에 따른 이용 범위를 관리합니다. 게이트웨이는 카탈로그 스냅샷을 갱신해 사용하며, 로그인 서버는 별도로 계정·토큰 발급을 담당합니다.

Gateway · 회사 대조

서브도메인과 JWT의 회사 ID가 모두 있으면 일치 여부를 확인합니다. 클라이언트의 직원 식별 헤더를 제거하고 검증된 회사·직원 정보로 다시 구성합니다.

업무 서비스 · 회사 조건

수주 서비스는 CurrentTenant의 회사 ID를 목록·합계·상세 조회 조건에 적용합니다. 기능 권한과 별도로 데이터 범위를 제한하며 필수 회사 정보가 없으면 거부합니다.

A사 사용자 기준 · 수주 조회의 허용·거부 사례
요청판정 지점처리
A사 프로젝트 조회업무 서비스현재 회사 조건에 맞는 데이터 조회
B사 프로젝트 ID 조회업무 서비스ID와 회사 ID를 함께 조회해 ‘찾을 수 없음’ 처리
A사 토큰으로 B사 접속게이트웨이서브도메인·토큰 회사 ID가 모두 있을 때 불일치 거부

검증 근거: 회사 컨텍스트를 바꿔 수주 목록·합계·ID·코드 조회의 격리를 확인하는 통합 테스트를 작성했습니다. 서브도메인 식별은 단계 적용 중이며, 카탈로그 미로드·회사 정보가 없는 전환기 토큰에서는 게이트웨이 대조를 생략하는 경로가 있습니다.

서비스별 DB 분리와 고객사 격리는 별개입니다. company_id만 추가해서 자동 격리되는 구조가 아니므로, 커스텀 쿼리에도 회사 조건을 적용하고 검증해야 합니다.

역할별 기능 권한

직원관리에서 역할·기능 권한을 관리하고 API 경로와 권한을 분리해 고객사별 역할 구성을 지원했습니다.

선택해서 쓰는 공통 모듈

10개 모듈과 Spring Boot 자동 설정을 제공하고, GitHub Packages에 모듈별로 배포했습니다. 13개 서비스에 공통 처리 규격을 적용했습니다.

고객사별 추가 항목

필드 정의·JSONB 저장·타입 및 필수값 검증을 공통화했습니다. 고객사마다 컬럼을 늘리는 대신 동적 검증과 검색을 관리했습니다.

도식은 주요 보호 API 흐름을 나타냅니다. 클릭하면 확대되며 확대 뷰어의 조작 UI는 영어입니다.

05 / Operations & Collaboration

구현 이후의 운영과 검증

현업·기획과 경계를 조율하고, 분리된 서비스의 장애를 추적하고 변경을 검증할 기반을 마련했습니다.

요구사항과 단계적 전환

현업·기획과 각 서비스가 소유할 데이터와 외부에 제공할 기능을 조율했습니다. 연차관리 파일럿을 거쳐 전환을 확장했고, 최근 생산·재고 연동과 품질 검사 기능은 일부 운영에 적용했습니다.

요청 추적과 관측

HTTP·Outbox·CDC·Kafka 구간의 추적 연결을 보완해 12개 서비스의 요청 흐름을 추적 ID로 확인하도록 했습니다. Prometheus·Grafana로 메트릭을 수집·시각화하고 임계치 알림을 연결했습니다.

테스트와 배포

팀과 함께 12개 서비스에 약 900개 테스트를 구축했습니다. 공용 워크플로우·Blue-Green·헬스체크·graceful shutdown으로 배포 절차를 정리했습니다.

배포 단계 테스트는 러너 제약으로 제외했으며, 머지 전 CI 연계는 남은 과제입니다.

AI는 설계 대안 비교·테스트 작성·리뷰 보조에 활용했습니다. 반례를 다시 검토하고 기존 코드·공식 문서·단위·통합 테스트 및 필요 시 부하 테스트로 검증했습니다. PR에서는 도메인 규칙·트랜잭션·N+1·동시성·예외 경로를 중점적으로 확인했습니다.
