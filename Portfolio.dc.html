BOM(자재 명세서)과 공정 순서를 작업 준비·실적·재고 처리로 연결했습니다. 생산 중 불량이나 재작업이 발생하면, 같은 공정·부품 관계를 따라 영향을 받는 범위와 수량을 다시 계산하도록 구성했습니다.

담당공정·BOM 모델링 · BFS 탐색 · 수량 역산 · 재고 연계

BOM은 제품에 필요한 부품과 수량을 나타냅니다

BOM(Bill of Materials, 자재 명세서)은 제품을 만드는 데 어떤 부품이 몇 개 필요한지 정리한 목록입니다. 조립품 아래에 하위 부품이 연결되는 계층 구조로 표현할 수 있으며, 생산할 제품 수량에 따라 필요한 부품 수량을 계산하는 기준이 됩니다.

BOM과 공정 순서를 실제 생산 흐름으로 연결했습니다

부품의 부모·자식 관계와 소요량 비율을 따라 필요 수량을 계산하고, 공정 템플릿의 순서대로 생산 경로를 구성했습니다. 작업 준비·완료 처리에서는 실적 기록과 재고 이동을 연결하고, 이전·하위 공정의 재고가 부족한 경우 완료 처리를 제한했습니다.

불량·재작업에서는 영향 범위와 수량을 다시 계산해야 했습니다

업무의 어려움

하위 부품 공정과 상위 조립 공정이 연결되어 있어, 재작업 시 어느 공정까지 얼마의 수량을 되돌릴지 판단해야 했습니다. 개별 수량을 수기로 계산하면 취소 시 원래 수량을 복원하는 작업도 복잡해졌습니다.

모델의 선택

공정의 이전·다음 관계와 BOM의 부모·자식 관계를 하나의 그래프로 표현했습니다. BFS로 처리 대상 경로를 탐색하고 BOM 소요량 비율에 따라 상·하위 부품 수량을 환산했습니다.

AFTER / 시스템 반영

  1. 불량 공정·수량 선택
  2. 재작업 시작 공정 선택

검증과 검색

정의되지 않은 항목과 잘못된 타입은 저장 전에 검증하고, 필수값·기본값과 타입별 값 정규화를 적용했습니다. 조회 시에도 회사·대상별 필드 정의를 기준으로 검색 조건을 구성하도록 했습니다.

선택과 비용

고객사별 추가 항목마다 DB 컬럼을 늘리는 부담을 줄인 대신, 동적 필드의 타입 검증과 검색 처리를 애플리케이션에서 관리하도록 했습니다.

역할에 필요한 기능 권한을 조합합니다

기능별 권한

업무 기능을 기준으로 권한을 나누고, 고객사가 필요한 권한을 조합해 역할을 구성하도록 했습니다. 각 API에는 @RequiresPermission으로 필요한 권한을 선언해, API 주소가 바뀌어도 역할 설정을 유지할 수 있게 했습니다.

변경 반영

권한 변경 커밋 후 Redis 캐시를 무효화하고, 무효화 실패에 대비해 TTL 10분을 적용했습니다. 캐시 미스·조회 실패 시 EMS에서 원본을 조회하며, 원본 조회도 실패하면 보호 API 접근을 거부하도록 했습니다.

게이트웨이 구축 · 인증부터 서비스 라우팅까지

기존 구조

기존에는 API 요청을 처리하기 전에 게이트웨이가 로그인 서버와 직원관리 서버를 호출해 인증·인가를 확인했습니다. 요청마다 내부 호출이 추가되고, 두 서버의 응답에 의존하는 구조였습니다.

변경 판단

요청 경로의 내부 호출과 의존성을 줄이기 위해 JWT 검증과 권한 판정을 게이트웨이로 옮겼습니다. JWT의 서명·만료·발급자는 로컬에서 검증하고, 권한은 Redis 캐시를 활용해 직원관리 서버(EMS)의 원본 조회를 줄였습니다. 토큰 폐기 여부를 확인하는 Redis 조회는 유지했습니다.

권한 확인을 통과한 요청은 회사·직원 정보를 담아 대상 서비스로 전달하며, 라우팅에는 서비스별 서킷 브레이커를 적용했습니다.

줄인 의존성과 늘어난 책임

요청마다 인증 서버에 토큰 검증을 위임하던 호출을 제거하고, 권한 캐시가 유효한 동안에는 EMS 조회를 생략했습니다. 대신 게이트웨이가 인증·인가 정책을 함께 책임지게 되었고, 토큰 폐기와 권한 변경을 반영하기 위한 캐시 관리가 필요해졌습니다.

권한 변경 시 캐시 무효화와 TTL을 적용하고, 캐시 미스·조회 실패 시 EMS에서 원본을 조회하도록 했습니다. 원본 조회도 실패하면 보호 API 접근을 거부합니다.
